# Migration Strategy Decision

Last updated: 2026-06-23

Status: recommended decision, not implemented.

## Decision

Use Supabase SQL migrations as the canonical database migration source for NXTTRACK.

Target location:

```txt
supabase/migrations/
```

Target package command:

```txt
pnpm run db:migrate
```

Recommended implementation direction:

- Use Supabase CLI-managed migration files.
- Apply migrations to staging through the deploy workflow.
- Keep seeds separate from schema migrations.
- Do not create schema until the staging Supabase project and exact CLI version/command are confirmed.

Official Supabase references:

- Database migrations: https://supabase.com/docs/guides/deployment/database-migrations
- CLI reference: https://supabase.com/docs/reference/cli/introduction
- Managing environments with migrations and GitHub Actions: https://supabase.com/docs/guides/deployment/managing-environments

## Why This Direction

NXTTRACK depends on:

- Supabase Auth.
- Supabase Postgres.
- Supabase RLS.
- Supabase Storage.
- Tenant-scoped schema and policies.

Keeping migrations as versioned SQL files makes tenant isolation, RLS policies, functions, indexes, and storage policy setup reviewable in pull requests.

## Current Deploy Workflow Assumption

The existing `.github/workflows/deploy.yml` already runs:

```txt
pnpm run db:migrate
```

That command does not exist yet because the app/package scaffold has not been created.

Phase 2 must define this command before the first real staging deploy.

## Recommended Command Shape

Final command is not locked until the scaffold and CLI version are confirmed.

Candidate direction:

```txt
pnpm run db:migrate
  -> supabase db push --db-url "$DATABASE_URL"
```

Notes:

- Supabase docs state that `supabase db push` pushes local migrations to a remote database and can use `--db-url`.
- Exact flags must be verified with `supabase --help` and `supabase db push --help` during implementation.
- The command must run non-interactively in GitHub Actions.
- The workflow should fail before release activation if migrations fail.

## Migration File Rules

- Migrations are append-only after merge.
- Migration filenames are generated by the Supabase CLI when possible.
- No hand-invented timestamp filenames unless the chosen tool explicitly requires it.
- Each migration should be small enough to review.
- RLS changes live in migrations next to table changes.
- Functions, views, triggers, and policies require extra review.
- Seeds do not belong in schema migrations.
- Demo seed is staging/dev only.

## Local Development Flow

Target flow after scaffold:

1. Start or connect local Supabase development stack.
2. Create migration through Supabase CLI.
3. Write SQL.
4. Apply locally.
5. Run type generation if configured.
6. Run tests.
7. Run Supabase advisors/security checks where available.
8. Commit migration file.
9. Deploy to staging through GitHub Actions.

## Staging Deployment Flow

1. Merge approved changes to `staging`.
2. Workflow installs dependencies.
3. Workflow builds app.
4. Workflow runs `pnpm run db:migrate` against staging database.
5. If migration fails, deployment stops.
6. If migration succeeds, release is activated.

## Production Policy Later

Production migrations require separate approval.

Production-specific rules to decide later:

- Whether production deploy requires manual approval after staging success.
- Whether destructive migrations require a separate migration PR.
- Backup/restore point requirements before migration.
- Roll-forward vs rollback policy.

## RLS And Security Requirements

Every migration touching user or tenant data must consider:

- RLS enabled on exposed tables.
- Policies use tenant and role predicates, not only `TO authenticated`.
- `UPDATE` policies include both `USING` and `WITH CHECK`.
- Authorization data must not rely on user-editable metadata.
- Service-role behavior is kept server-only.
- Views should not accidentally bypass RLS.
- `SECURITY DEFINER` functions require explicit justification and restricted execution.

## Acceptance Criteria Before First Schema Migration

## What Not To Do Yet

- Do not create database schema in this PR.
- Do not run migrations against staging yet.
- Do not connect Supabase Auth yet.
- Do not add service-role usage in app code yet.
